# 0004. 10^8 규모 풀을 위한 디스크 기반 라이브러리 저장소

## 맥락
CSV 입력은 검증·지문 생성 후 메모리에 올린다. 2,048비트 지문을 바이트 하나로 저장하면 100만 개에 약 2 GB라 10^6개 근처가 실용 한계였다. 목표 풀은 10^8개다.

## 결정
`prepare-library`가 CSV를 `resources.cpu_threads`개 프로세스로 스트리밍 처리해 ID 정렬 NumPy 열(`compound_id`, `smiles`, `source`, 선택적 `scores`)과 비트 압축 `fingerprints.npy`, `library.json`(설정·입력 해시·파일 체크섬)을 만든다. 실행 시 열은 memory-map하고 지문은 추론 배치 단위로만 푼다. CSV 경로와 똑같은 검증·정규화·중복 제거·대표 규칙을 적용해, 같은 입력이면 CSV 실행과 저장소 실행의 과학적 기록이 정확히 같다. CSV와 저장소 모두 `Library`/`PackedFingerprints` 같은 객체를 통해 같은 파이프라인 코드를 탄다.

## 대안
- **CSV를 메모리에 올리는 기존 경로만 유지**: 밀집 uint8 지문만으로 10^8개에 약 204.8 GB가 필요해 목표 규모에서 쓸 수 없다. 10^6개 이하 풀에서는 지금도 이 경로를 쓴다.
- **밀집 uint8 지문을 디스크에 두고 memory-map**: 비트 압축보다 디스크가 8배 크다(204.8 GB 대 25.6 GB).

## 결과
- 저장소를 만든 설정(지문 종류·반경·비트, 중복 제거, invalid_policy, 열 이름, replay 점수 열)이 실행 설정과 다르면 실행이 시작 전에 실패한다. 설정을 바꾸려면 저장소를 다시 만들어야 한다.
- 저장소를 열 때 모든 파일 체크섬을 검증하므로 부분 복사·손상은 질의 전에 드러난다. 구축 실패 시 부분 산출물은 삭제된다.
- 위치가 곧 ID 순서이므로 라이브러리 정렬을 깨는 변경은 동점 처리·replay 점수 조회(이진 탐색)를 모두 깨뜨린다.
- 홀드아웃 분할은 여전히 모든 구조를 파싱하므로 대형 저장소에서는 `holdout_fraction: 0`을 쓴다.
- 트리·foundation 백엔드는 획득 행을 풀어서 메모리에 올리므로 저장소가 이들의 메모리 비용까지 줄이지는 않는다.
